# Mini NPU Simulator

숫자 배열로 표현한 십자가(Cross)와 X 패턴을 비교하는 Python 콘솔 프로그램입니다. 입력 패턴과 두 필터의 같은 위치에 있는 수를 곱하고 모두 더한 MAC 점수로 어느 쪽에 가까운지 판정합니다.

## 실행 방법

Python 3.8 이상이 필요합니다. NumPy 같은 외부 패키지는 설치하지 않아도 됩니다. `main.py`, `data.json`을 같은 폴더에 두고 터미널에서 아래 명령어를 실행합니다.

```powershell
python main.py
```

메뉴에서 `1`을 누르면 3×3 직접 입력, `2`를 누르면 제공된 `data.json`을 분석합니다. Windows에서 `python` 명령어가 인식되지 않으면 `py main.py`를 시도할 수 있습니다.

### 모드 1: 직접 입력

필터 A와 필터 B를 각각 3줄 입력한 다음 패턴을 3줄 입력합니다. 한 줄에는 공백으로 구분한 숫자 3개를 적습니다.

필터 A (십자가):

```text
0 1 0
1 1 1
0 1 0
```

필터 B와 입력 패턴 (X):

```text
1 0 1
0 1 0
1 0 1
```

이 값을 입력하면 A 점수는 1, B 점수는 5이므로 `B`로 판정됩니다. 출력 형식의 예시는 다음과 같으며 실행 시간은 PC마다 달라집니다.

```text
[3] MAC 결과
A 점수: 1
B 점수: 5
판정: B
연산 시간(평균/10회): ... ms (A 필터 기준)
```

`0 1`처럼 숫자를 2개만 적거나 `0 a 1`처럼 문자를 입력하면 오류 문구와 올바른 입력 예시를 보여 주고 **해당 행을 다시** 입력받습니다. `nan`, `inf` 같은 유한하지 않은 숫자도 입력받지 않습니다.

### 모드 2: JSON 분석

`data.json`의 `filters`에서 `size_5`, `size_13`, `size_25` 필터를 읽고, `patterns`의 각 항목을 차례대로 판정합니다. 패턴 키는 `size_N_idx` 형식이며 N에 해당하는 필터를 사용합니다. 예를 들어 `size_13_2`는 `size_13` 필터로 분석합니다.

필터 키가 누락되었거나 행렬의 크기가 틀리면 이유를 출력합니다. 필터를 사용할 수 없는 케이스는 건너뛰어 성공으로 처리하지 않고 **FAIL로 집계**하며, 다음 케이스의 분석은 계속 진행합니다. `size_N_idx` 형식이 아닌 키나 잘못된 라벨도 해당 케이스의 FAIL 사유로 출력합니다. 다만 JSON 파일 자체를 읽을 수 없거나 최상위 구조가 잘못되었다면 오류를 안내하고 분석 모드를 종료합니다.

## 구현 요약

### MAC 점수

배열은 Python의 2차원 리스트로 저장하며 `matrix[row][col]`로 위치별 값을 읽습니다. `mac()`는 다음과 같이 행과 열을 차례대로 돌며 곱한 값을 `total`에 누적합니다.

```python
total = 0.0
for row in range(size):
    for col in range(size):
        total += pattern[row][col] * filter_matrix[row][col]
```

즉, 같은 위치의 곱셈 → 누적 합산 → 두 필터 점수 비교 순서입니다. 점수가 높을수록 **현재 필터와의 가중 곱 합계가 크다**는 뜻이지만, 이것을 0~1 사이의 확률이나 모든 데이터에 공통인 유사도 점수로 해석할 수는 없습니다. 필터 가중치와 입력값에 따라 값의 범위가 달라지기 때문에 별도 점수 정규화나 절대 임계값은 두지 않았습니다. 현재 구현은 한 행의 왼쪽부터 오른쪽으로 누적한 뒤 다음 행으로 넘어갑니다. 부동소수점에서는 덧셈 순서에 따라 아주 작은 차이가 생길 수도 있습니다.

### 라벨 정규화와 동점 규칙

`normalize_label()`에서 앞뒤 공백을 제거하고 소문자로 바꾸어 `+`, `cross`, `Cross`, ` CROSS `를 `Cross`로, `x`, `X`, ` x `를 `X`로 통일합니다. 입력 데이터의 기호와 프로그램의 출력 이름이 다르더라도 같은 뜻이면 정상 비교하도록 하기 위해서입니다. 규칙을 함수 하나에 모아 두면 JSON 로드와 예상 정답 비교에서 재사용하기 쉽고, 확인할 곳도 명확해집니다. 지원 라벨이 더 생긴다면 변환 규칙과 필터·예상 정답의 테스트 사례도 함께 추가해야 합니다. 현재 프로그램은 **Cross와 X 두 종류만** 지원합니다.

`decide()`는 점수 차이의 절댓값이 `1e-9`보다 작으면 `UNDECIDED`로 처리합니다. `1e-9`는 미션에서 제시한 권장 기준을 선택한 값입니다. 0.9와 0.8999999999999999처럼 소수 계산에서 생기는 미세한 차이를 동점으로 보기 위한 것이며 모든 크기와 모든 수치 범위에 언제나 최적인 기준이라는 뜻은 아닙니다. 필터 가중치가 훨씬 커지면 상대오차를 함께 고려하는 방식도 검토할 수 있습니다. 임의로 epsilon을 키워 정답을 맞추지는 않았습니다.

- **모드 1:** 동점이면 `판정 불가 (UNDECIDED)`를 보여 줍니다. 정답 라벨을 받지 않으므로 PASS/FAIL은 매기지 않습니다.
- **모드 2:** 동점이면 `UNDECIDED`를 보여 주며, expected가 Cross 또는 X인 경우 일치하지 않아 FAIL로 집계합니다. 점수와 예상 라벨을 함께 확인할 수 있습니다.

### 성능 측정

`perf_counter()`로 `mac()` 호출 전후만 재며 파일 읽기, 입력, 출력 시간은 제외합니다. 초기 실행 영향을 줄이기 위해 3회 워밍업을 실행한 다음, **10회 측정 평균과 최소·최대(ms)**를 출력합니다. 최소/최대는 실행할 때마다 시간이 달라지는 정도를 파악하는 참고값입니다. 별도 NPU 벤치마크는 아닙니다.

## 결과 리포트

### 제공된 데이터 분석 결과

제공된 `data.json`을 그대로 사용한 결과입니다. 테스트를 통과하도록 expected나 필터 값을 임의로 수정하지 않았습니다.

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
| --- | ---: | ---: | --- | --- | --- |
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.70000000000001 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

**총 6개 / PASS 3개 / FAIL 3개**입니다.

### 실패 원인 분석

1. `size_5_1`은 두 점수가 약 0.9로 거의 같아 `UNDECIDED`가 나왔습니다.
2. expected는 X이지만 판정이 X가 아니므로 FAIL입니다.
3. `size_13_2` 역시 Cross와 X 점수 차이가 `1e-9`보다 작습니다.
4. expected는 Cross이지만 동점 정책에 따라 FAIL입니다.
5. `size_25_1`도 같은 이유로 `UNDECIDED` 및 FAIL입니다.
6. 이 세 사례는 데이터 파일을 읽지 못해서 발생한 오류가 아니라 **점수 비교 정책에 따른 결과**입니다.
7. 예를 들어 0.9와 0.8999999999999999를 `==`로 비교하면 소수 표현 오차 때문에 서로 다른 수로 보일 수 있습니다.
8. 그래서 `abs(score_a - score_b) < EPSILON`으로 아주 작은 차이를 동점 처리합니다.
9. `+`와 `Cross`, `x`와 `X`도 사전에 같은 표준 라벨로 바꾸지 않으면 불필요한 FAIL이 생길 수 있습니다.
10. 행 수, 열 수, 숫자 형식이 잘못된 경우는 **데이터/스키마 문제**로 구분합니다.
11. 점수가 충분히 다른데 잘못 판정된다면 인덱스나 필터 선택 순서 같은 **로직 문제**를 살펴봐야 합니다.
12. 점수가 극히 가깝다면 **수치 비교 문제**를 먼저 확인하고 차이와 epsilon 값을 함께 살펴봅니다.
13. 동점의 원인을 확인할 때는 케이스 ID, Cross 점수, X 점수, expected, 실제 판정을 출력해 비교합니다.
14. 필터의 전체 2차원 배열까지 기록하는 스냅샷 기능은 넣지 않았습니다. 현재 실패 사유 파악에는 점수와 라벨 기록이면 충분하다고 판단했습니다.

### 연산 횟수와 시간 복잡도

| 크기 | MAC의 위치별 곱셈 횟수(N²) | 평균 시간(ms), 사용자 실행 예시* |
| --- | ---: | ---: |
| 3×3 | 9 | 0.010530 |
| 5×5 | 25 | 0.004760 |
| 13×13 | 169 | 0.023610 |
| 25×25 | 625 | 0.046290 |

*기록된 측정 예시: Windows PowerShell, Python 3.15.2, 각 크기별 10회 평균. CPU 모델은 기록하지 않았습니다. 위 값은 **수정 전 프로그램의 실제 출력 기록**이며, 수정 후 코드의 워밍업 및 최소·최대 출력 결과와는 달라질 수 있습니다. 최신 측정값은 직접 실행한 콘솔 결과를 참고합니다.*

MAC은 N개의 행마다 N개 열을 전부 순회하므로 위치별 곱셈 횟수는 `N × N`, 시간 복잡도는 **O(N²)**입니다. N이 5에서 25로 5배 늘어나면 연산 수는 25에서 625로 25배 늘어납니다. 이때 패턴과 필터를 2차원 배열로 저장하므로 저장 공간도 각각 O(N²)가 필요합니다. 실측 시간이 이론적 연산 횟수와 같은 비율로 늘어나지 않는 이유는 함수 호출, 반복문, 캐시, 운영체제 스케줄링 등 고정 비용과 실행 환경의 영향 때문입니다. 3×3 측정 시간이 5×5보다 크게 나온 것도 이러한 작은 측정 구간의 변동 가능성을 보여 줍니다.

### 1000×1000처럼 크기가 커진다면

현재 필수 지원 크기는 최대 25×25입니다. **1000×1000 입력을 별도로 테스트하거나 최적화했다고 주장하지 않습니다.** 다만 이 크기에서는 한 번의 MAC에 1,000,000번의 위치별 곱셈과 누적 덧셈이 필요해집니다. 25×25의 625회에 비하면 약 1,600배의 위치를 계산합니다. 시간 복잡도는 여전히 O(N²)지만 실제 실행 시간은 환경에 따라 다릅니다.

입력 패턴과 필터 2개가 각각 100만 개의 숫자를 가지면 총 300만 개 원소를 저장해야 합니다. 64비트 실수 원소만 빽빽하게 저장한다고 가정하면 최소 약 24MB(원소당 8바이트)지만, **Python 리스트와 float 객체로 저장하는 실제 메모리 사용량은 훨씬 클 수 있습니다.** JSON 파싱 과정의 임시 객체와 추가 데이터까지 고려해야 합니다.

향후 개선 방향으로는 중첩 리스트 대신 1차원 연속 저장 구조를 이용해 접근 패턴을 단순화하거나, 데이터를 작은 블록 단위로 다루어 캐시 활용을 고려할 수 있습니다. 다만 블로킹이 항상 빨라지는 것은 아니므로 같은 입력·반복 횟수에서 측정해야 합니다. NumPy 벡터화는 일반적인 최적화 선택지이지만 **이번 미션은 외부 라이브러리가 금지되어 있어 구현에 사용하지 않았습니다.** 현재 구현이 1000×1000을 빠르게 처리한다고 보장하지도 않습니다.

### CPU와 NPU 처리 방식 비교

일반적인 CPU는 다양한 종류의 작업과 복잡한 제어 흐름에 대응하는 데 강점이 있습니다. 이 Python 프로그램은 CPU 위의 반복문에서 MAC을 순차적으로 계산하므로 Python 반복문 실행 비용도 시간에 포함됩니다. 이 구현 자체를 실제 NPU 연산 속도로 해석하면 안 됩니다.

NPU는 많은 곱셈·누적 연산을 병렬 처리하도록 설계된 전용 연산 장치를 활용합니다. 같은 작업을 충분히 크게 묶어 처리할 수 있다면 높은 처리량을 기대할 수 있지만, 무조건 CPU보다 빠르다는 뜻은 아닙니다. CPU에서는 반복문과 명령 처리 비용, 캐시 미스, 메모리 대역폭이 병목이 될 수 있습니다. NPU에서도 연산 장치가 데이터 공급 속도를 앞지르면 메모리 대역폭이나 온칩 데이터 이동이 병목이 됩니다. CPU 메모리에서 NPU로 데이터를 옮기는 전송 비용, 연산 실행 준비 비용도 작은 작업에서는 상대적으로 크게 작용할 수 있습니다. 따라서 큰 MAC 작업에서는 **연산 자체의 병렬화뿐 아니라 메모리 접근, 데이터 재사용, 전송량 축소**가 중요합니다.

이번 프로그램은 NPU를 직접 사용하는 것이 아니라 MAC 연산과 병목 원리를 학습하기 위한 **CPU 기반 시뮬레이터**입니다.

## 확인할 테스트

- 정상 직접 입력: 십자가 A, X B, X 패턴을 입력하면 A=1, B=5, 판정 B가 나오는지 확인합니다.
- 입력 오류: 숫자 개수 부족, `0 a 1`, `nan` 등을 넣었을 때 그 행의 재입력을 요구하는지 확인합니다.
- JSON 분석: 제공된 6개 케이스에서 PASS 3개, FAIL 3개와 상세 점수를 확인합니다.
- 스키마 오류: `data.json` 복사본에서 케이스의 행 하나를 제거하거나 키를 바꾸었을 때 해당 케이스만 FAIL로 기록되는지 확인할 수 있습니다. 테스트 후 원본 JSON으로 복원해야 합니다.
- epsilon 테스트 아이디어: `decide(0.9, 0.8999999999999999)`는 `UNDECIDED`, `decide(1, 0)`은 A입니다. epsilon을 바꿔 테스트한다면 정책도 README에 함께 갱신해야 합니다.

위의 오류 주입 및 epsilon 테스트 아이디어는 추가 확인 방법이며, 별도 자동화 테스트를 수행했다는 의미는 아닙니다.
